# AGENTS.md

Guidance for AI coding agents working on pylibtiff.

## What this project is

`pylibtiff` (import name `libtiff`) provides two largely independent TIFF implementations:

1. **ctypes wrapper around the system libtiff C library** — `libtiff/libtiff_ctypes.py` (`TIFF`, `TIFF3D`).
2. **Pure-Python TIFF/LSM reader/writer** built on `numpy.memmap` — `tiff_file.py` (`TIFFfile`),
   `tiff_image.py` (`TIFFimage`), `tiff_array.py`, `tiff_files.py`, `tiff_channels_and_files.py`,
   `tiff_sample_plane.py`, `tiff_data.py`, `lsm.py` (Zeiss LSM tags), `lzw.py`.

Plus two C extensions compiled with the numpy C API (`libtiff/src/bittools.c`, `libtiff/src/tif_lzw.c`)
and two console scripts (`libtiff.info`, `libtiff.convert` in `libtiff/scripts/`).

Upstream is `pearu/pylibtiff` on GitHub; default branch is `master`.

## Layout

```
libtiff/
  __init__.py           public API re-exports; imports libtiff_ctypes eagerly
  libtiff_ctypes.py     ctypes bindings, library discovery, tag/field type tables
  tiff_h_X_Y_Z.py       #define constants extracted from tiff.h, one file per libtiff version
  tiff.py               aliases for the pure-Python API (TIFFfile, TIFFimage, TiffArray)
  src/*.c               C extensions (bittools, tif_lzw)
  scripts/              console entry points
  tests/                pytest suite
  test_bittools.py      stray test module outside tests/ (not run by CI)
  version.py            generated by setuptools_scm; never edit or commit
setup.py                extension + package metadata (most metadata lives here, not pyproject)
pyproject.toml          build requirements + setuptools_scm config
setup.cfg               flake8 and coverage config
.conda/environment.yml  CI test environment
```

## Environment and build

- The C extensions must be built before anything imports: `pip install --no-deps -e .`
  (or `python setup.py build_ext --inplace`). If you see
  `ImportError: cannot import name 'tif_lzw' from 'libtiff'`, the extensions are not built for the
  active interpreter.
- A shared libtiff must be discoverable via `ctypes.util.find_library('tiff')`. CI uses conda-forge
  `libtiff` (and one job with Ubuntu's `libtiff-dev`).
- Versions come from git tags via setuptools_scm; `libtiff/version.py` is generated.

## libtiff version header modules (important)

At import, `libtiff_ctypes.py` asks the loaded library for its version and imports
`libtiff.tiff_h_<major>_<minor>_<patch>`. **If no such module exists, importing `libtiff`
parses the installed `tiff.h` and writes a new `tiff_h_*.py` into the package directory.**

Consequences for agents:
- Merely running `python -c "import libtiff"` or the tests can create an untracked
  `libtiff/tiff_h_*.py` in the working tree. Check `git status` afterwards and delete it unless
  adding support for that libtiff version is the actual task.
- When adding a new libtiff version, generate the file against a clean install of exactly that
  version, then diff it against the previous version's module to check the constants look sane.
  Commit only the new `tiff_h_*.py` (see commit 9363dc7 for 4.7.0). What you need is a libtiff
  install of exactly that version, with its `tiff.h` included. The recipe below uses conda-forge
  (`mamba` works as a drop-in replacement for `conda`). If `conda` isn't available, ask the user
  how to get that libtiff version rather than installing a package manager yourself. Procedure
  that works (Linux):

  ```bash
  # Run from the repo root. Keep the env out of the working tree so it doesn't show in git status.
  REPO=$PWD
  SCRATCH=/some/scratch/dir
  ENV=$SCRATCH/env_X.Y.Z
  conda create -y -p $ENV -c conda-forge --override-channels python=3.12 numpy pytest "libtiff=X.Y.Z"
  # Run from outside the repo so the header search can't pick up a stray tiff.h in the CWD.
  # The trailing ImportError about tif_lzw is fine if the C extensions aren't built for this Python.
  (cd $SCRATCH && LD_LIBRARY_PATH=$ENV/lib PYTHONPATH=$REPO $ENV/bin/python -c "import libtiff")
  # Check the version detected and which module is used:
  LD_LIBRARY_PATH=$ENV/lib PYTHONPATH=. $ENV/bin/python -c \
      "import libtiff.libtiff_ctypes as l; print(l.libtiff_version, l.tiff_h.__name__)"
  diff libtiff/tiff_h_<prev>.py libtiff/tiff_h_X_Y_Z.py
  ```

  Setting `LD_LIBRARY_PATH` makes `ctypes.util.find_library` resolve the env's libtiff rather
  than the system one. Confirm this by checking the `Generating ... from ...` message.
  Generated modules are frequently identical across releases (4.5.1–4.7.0 are byte-identical).
- Do not hand-edit existing `tiff_h_*.py` modules; they are generated data (and excluded from
  coverage in `setup.cfg`).

## Tests

```bash
pytest -s libtiff/tests                   # what CI runs (plus --cov=libtiff)
pytest -s libtiff/tests/test_libtiff_ctypes.py -k custom_tags
```

- Tests use pytest function style and the `tmp_path` fixture for files; follow that.
- Tests that exercise ctypes code use `pytest.importorskip('libtiff.libtiff_ctypes')`.
- `libtiff/test_bittools.py` is outside `tests/` and is not run by CI.
- **Always pass `-s`.** `test_copy` asserts on libtiff's stderr warnings ("legacy Deflate codec")
  and fails when pytest captures output.
- Crashes (segfaults) in ctypes code kill the whole pytest process. Isolate with `-k` when
  investigating, and keep references to ctypes callbacks alive (see the module-level
  `extenders` list in `test_libtiff_ctypes.py`) — garbage-collected callbacks crash later.

## Lint and style

```bash
flake8 libtiff/
```

- `libtiff_ctypes.py` (`# flake8: noqa for F821` acts as a file-wide noqa) and `scripts/*.py`
  are effectively not linted. Don't rely on CI lint to catch mistakes there.
- Max line length 120; docstring (`D`) checks are disabled in `setup.cfg`. CI installs
  `flake8-bugbear` and `flake8-debugger`, so bugbear warnings fail the build.
- Match the surrounding code: legacy modules use `%`-formatting and camel-case libtiff names
  (`SetField`, `GetField`, `read_image`); don't reformat or modernize code you aren't changing.
- Keep diffs minimal and focused; the maintainer reviews small, targeted PRs.

## ctypes wrapper pitfalls

- Every libtiff function called must have correct `argtypes`/`restype` declared. A missing
  `restype` defaults to `c_int` and silently truncates 64-bit pointers/offsets.
- Variadic functions (`TIFFSetField`, `TIFFGetField`, `TIFFVSetField`) are ABI-sensitive,
  especially on arm64/macOS where variadic args are passed differently. Test on multiple
  platforms or rely on CI's Windows/macOS/Linux matrix.
- Tag value types differ between libtiff 3.x and 4.x (e.g. `uint32` vs `uint64` for offsets
  and counts); gate on `libtiff_version_tuple` when behaviour changes by version.
- Custom tags are registered through a tag extender callback; the Python callback object must
  outlive every `TIFF` object that uses it.

## CI

`.github/workflows/ci.yaml`: flake8 lint job, then pytest across Windows/Ubuntu/macOS and
several Python versions using conda-forge libtiff, one job against system libtiff, and one
experimental job with numpy nightly wheels. Dependabot bumps GitHub Actions versions.

See `RELEASING.md`: tag `vX.Y.Z` on `master`, push with `--follow-tags`, create a GitHub
Release; the deploy workflow publishes to PyPI. Agents should not tag or release.
